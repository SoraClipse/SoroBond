# Issues #13–#16 — integration boundaries

These are application-side modules and do not change the on-chain contract. Node >=22.16 is required. Run `node --test packages/sdk/test/*.test.mjs apps/api/test/*.test.mjs apps/web/tests/*.test.mjs`; run the UI with `node apps/api/src/web-server.mjs` and open `http://127.0.0.1:8788/warranties/new`.

The RPC client pins official Soroban RPC URLs per network and validates the network passphrase before simulation and submission. Callers must assemble and sign using audited wallet software: the SDK does **not** hold secret keys, assemble XDR, or promise execution before a CONFIRMED result. This is read-only simulation plus signed-envelope submission and polling, not a complete wallet integration.

The warranty indexer persists checkpoint/event snapshots atomically and deduplicates by ledger/transaction/event index; the supplied `readRange` callback MUST guarantee complete contiguous finalized ranges (including empty ledgers) and authentic contract events. Its identity comparison is not cryptographic: operator must validate Soroban RPC event ledger/contract authenticity. Reorg/rollback must call `rollback` and save. Do not use a mutable shared temporary file across concurrent instances. Storage uses JSON checkpoint snapshots; use a transactional DB and durable locking in production. Event retention requires operational archive handling.

The evidence vault encrypts private data using AES-256-GCM, binds its commitment to warranty ID, enforces a size cap, access allowlist and expiration, but presently stores ciphertext **in memory**. Production requires authenticated wallet-backed server sessions, externally managed rotated keys, encrypted durable storage, audit/retention policies, and verification of resolver identity. The current `actor` string MUST come from trustworthy authentication, never directly from an HTTP parameter. Never put personal photos or raw evidence on a public chain.

The buyer/seller screen collects exact terms, locks inputs after review and requires wallet adapter connections and signatures for a single digest. The demo wallet adapter is NOT implemented; collected signatures are not independently validated yet. A production deployment must verify signatures, domain/network and public keys server-side/on-chain before funds move. No real escrow settlement or contract deployment is demonstrated. **Do not deposit real funds**: the underlying contract lacks release/claim settlement paths.
